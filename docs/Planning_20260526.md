# スクレイピング済みデータのDB投入計画
作成日: 2026-05-26

## 目的

これまでにスクレイピング済みのデータを、抜け漏れを確認しながら一通りDBへ投入する。
単純な一括投入ではなく、投入前の棚卸し、投入順序の固定、検証、失敗時の差し戻しまでを含めて進める。

## 前提

- スクレイピング済み成果物は `scraper/data/` 配下にある。
- DB投入は既存の `scripts/db/upsert_games.py` と関連スクリプトの流れを基本にする。
- 既存のテーブル設計と正規化方針は `docs/flow.md` と `docs/table_definition.md` を基準にする。

## 進め方

### 1. データ棚卸し

- `scraper/data/` 配下のJSON、CSV、補助ファイルを一覧化する。
- シーズンごと、対象競技データごとに件数を確認する。
- 重複、欠損、形式ゆれがないかを事前に確認する。
- どのファイルをDB投入対象にするかを明確にする。

### 2. 投入順の確定

投入は、参照整合性を崩しにくい順に進める。

1. teams
2. players
3. games
4. game_team_stats
5. player_game_stats

必要に応じて、ID名寄せやプロフィール補完などの正規化処理を先に挟む。

### 3. 事前チェック

- ローカルのサンプルデータで投入処理を再実行し、エラー有無を確認する。
- 既存DBに同一キーがある場合の上書き方針を確認する。
- 1シーズン分または1期間分を先行投入して、レコード数と主キー衝突を確認する。

### 4. 本投入

- シーズン単位または月単位で区切って投入する。
- 1バッチごとに件数とエラーを記録する。
- 途中失敗があれば、そのバッチのみ再実行できる粒度にする。
- 進行中の変更は都度メモして、後から追跡できるようにする。

### 5. 検証

- テーブルごとの件数を確認する。
- 主要な外部キーの欠損がないか確認する。
- 代表試合、代表選手について画面・SQLの両方で目視確認する。
- 異常値やNULLの増加があれば、その場で原因を切り分ける。

### 6. 差し戻し方針

- 失敗バッチは個別に再投入する。
- 誤投入が広がった場合は、対象期間のみ削除して再投入する。
- 影響範囲が不明な修正は、先に小さい範囲で再現確認してから進める。

## 実施単位のおすすめ

- まずは 1 シーズン分で試行する。
- 問題がなければ、同じ手順で全シーズンに展開する。
- 期間が長いデータは月単位で分割する。

## 完了条件

- 対象データがDBに投入済みである。
- テーブルごとの件数と主要キー整合性が確認済みである。
- 再実行手順と差し戻し手順が残っている。
- 途中で見つかった例外は別途メモ化されている。

## 補足

この計画は、投入作業の手順を先に固定してから実行するためのもの。
実作業で見つかった差分や例外は、必要に応じて `docs/flow.md` や関連メモに反映する。

## 実行チェックリスト

### 本体

- [x] `scraper/.env` に `SUPABASE_URL` と `SUPABASE_SECRET_KEYS` が設定されていることを確認する。
- [x] `scraper/data/` 配下が月次JSON中心の構成になっており、日次JSONや確認用JSONが除去済みであることを確認する。
- [x] `scraper/data/season_2016-2017/` から `scraper/data/season_2024-2025/` まで、投入対象の月次JSONが揃っていることを確認する。
- [x] `scraper/data/season_2022-2023/` に命名統一済みのファイル群がまとまっていることを確認する。
- [x] `python -m scripts.db.upsert_games --input <対象月次JSON> --dry-run` を代表シーズンで実行し、変換エラーが出ないことを確認する。
- [ ] まずは 1 シーズン分を対象に、月次JSONを古い月から順に投入する。
- [ ] 各月次JSON投入後に、`games`、`game_team_stats`、`players`、`player_game_stats` の件数増分を確認する。
- [ ] 1 シーズン分の投入結果に問題がなければ、残りシーズンも同じ手順で横展開する。
- [ ] 全シーズン投入後に、主要テーブルの件数と代表レコードを目視確認する。

### 保留

- [ ] `player_alias_candidates.csv` を使った `player_id_map` の名寄せ適用を今回の本投入に含めるか決める。
- [ ] `players.csv` と `players.json` のどちらを長期的な正本マスタとして扱うか決める。
- [ ] `game_team_stats_preview.csv` を今後も確認用ファイルとして保持するか決める。
- [ ] `play_by_play` 系データを今後も完全に切り離すか、別用途で保管するか決める。
- [ ] DB投入後にプロフィール補完を再実行するか決める。

### 要手動確認

- [ ] Supabase 側の接続先が本番投入先として正しいことをダッシュボード上で確認する。
- [ ] `SUPABASE_SECRET_KEYS` に設定した値が `service_role` キーであることを確認する。
- [ ] 既存DBに手作業で投入済みのデータがある場合、今回の upsert と衝突しないことを確認する。
- [ ] `player_id_map` テーブルを本当に使うか、現在のスキーマと運用を確認する。
- [ ] 投入後に確認する SQL 件数チェックの観点を先に固定する。
- [ ] 誤投入時の差し戻し対象期間と削除手順を、実行前に手元メモへ明記する。
